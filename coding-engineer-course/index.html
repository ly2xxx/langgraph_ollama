Inside the Coding Engineer
01

A Robot That Codes Until It's Done

What the Coding Engineer is, why it exists, and what happens after you hand it a goal.

You give it one sentence. It works until the job is checkably finished.

The Coding Engineer is an AI agent that takes a folder of code plus a plain-English goal, like "implement the string-calculator kata so all scenarios pass". It then writes code, tests it, fixes what broke and tests again, with nobody watching.

A chatbot gives you code and hopes. This agent doesn't hope. It refuses to call a job done until automated tests pass and a second AI has tried to find a cheat.

🎯

Goal-driven

It stops when a test says "done", not when the AI feels done.

🔁

Self-correcting

Each failed test becomes a written "lesson" that feeds the next attempt.

🧱

Sandboxed

It never touches your real files. You review its work and decide whether to keep it.

🛑

Knows when to quit

If it's going in circles, it stops and writes you a report instead of burning money.

The fun part: it has already rewritten itself

Look in the project's diary/ folder and you'll find a run where the agent was pointed at its own code. The goal was to upgrade its "maker" component from an old library feature to a newer one. It did it in 3 attempts. The commit it produced is in the real history today.

2

💡
The core idea: verification beats intelligence

A mediocre model inside a loop with honest tests will usually beat a brilliant model that just guesses once. The model doesn't do the clever part of this project. The loop around it does. Most of what you'll learn here is about that loop.

02

Ten Rooms and a Clipboard

The agent is a board game: ten squares, arrows between them, and one shared clipboard that every square writes on.

It's a board game, not a brain

Think of Snakes and Ladders. There are fixed squares, arrows between them, and a rule at certain squares that decides where you go next. A bad roll sends you back down a snake. The Coding Engineer works the same way, and engineers call this shape a state machine.

It's built with LangGraph. Each square is a node, and each arrow is an edge. Click any square below.

💡
Keep decisions and work apart

Nodes do work and routers decide, and they're never mixed. When an agent misbehaves you can read the routers to see exactly why it went where it went. A good instruction for an AI tool: "keep routing logic in pure functions, separate from the nodes."

Sealing the Exam Before Studying

How the agent writes its own definition of done, then locks it so it can never quietly lower the bar.

The temptation every AI coder faces

Picture a student who writes their own exam and can edit it while taking it. You can guess how they'd do. An AI told "make the tests pass" faces the same temptation: the cheapest fix is often to weaken the test.

The Coding Engineer's answer works like a sealed envelope. The exam is written first and sealed. The student can read it any time but can never change a word.

Two testing styles

Writing a whole feature file plus step code in one AI call is the most fragile request in the loop. Weaker models can pick test_style="pytest", which skips BDD. The acceptance criteria become the contract, and the maker must write ordinary pytest tests alongside its code.

CODE · tools/code_exec.py 
    def _check_frozen(self, real_path: Path, op: str) -> None:
        try:
            rel = real_path.relative_to(self.root)
        except ValueError:
            rel = real_path

        # .git internals are always frozen, even if never explicitly listed.
        if rel.parts and rel.parts[0] == ".git":
            raise JailViolation(f"{op} refused: {rel} is inside .git, which is always frozen")

        for frozen_rel in self.frozen:
            if rel == frozen_rel or self._is_relative_to(real_path, self.root / frozen_rel):
                raise JailViolation(f"{op} refused: {rel} is frozen and cannot be modified")

Before any write/delete/move, check whether the target is off-limits.

Try to express the path relative to the sandbox root…

…e.g. turn "C:/…/worktree/features/x.feature" into "features/x.feature".

If that's impossible…

…just use the path as-is.

 

Git's own bookkeeping folder is always off-limits:

if the path starts with ".git"…

…refuse, with an error message saying exactly why.

 

For every frozen file or folder on the list…

…if this path IS it, or sits inside it…

…refuse. The maker sees this text as a tool error and learns from it.

💡
Loud refusals beat silent ones

The jail raises an exception instead of quietly ignoring bad writes. The tool turns that into an ERROR: … message the AI can read. A blocked action that fails silently teaches the AI nothing and hides bugs from you. A clear refusal is useful feedback.

04

Two Brains: Makers and Checkers

Why one AI model proposes and builds, while a different, colder one judges and audits.

Never let the contestant judge the contest

An architecture competition doesn't let the entrants score their own designs. An independent jury does. This agent follows the same rule. Every AI call asks for one of two roles, and the roles can be filled by different LLMs.

🛠️
primary: the contestant

Intake, writing scenarios, proposing plans, coding, diagnosing. These are the frequent, creative calls inside the loop.

⚖️
secondary: the jury

Scoring plans, checking adopted scenarios, adversarial review. These are the independent judgments. If not configured, it falls back to the primary model, so the loop still works with one.

CODE · nodes.py (_score_plans) 
    secondary = _eng().get_llm("secondary", temperature=0.0)
PLAIN ENGLISH

"Give me whichever model plays the jury role, at zero temperature." No node ever builds a model by hand. They all go through get_llm(role), so swapping models is a settings change, not a code rewrite.

propose plans · primary · 0.8Hot: we want three genuinely different ideas
write scenarios · primary · 0.3Slightly warm: some variety, mostly careful
code (maker) · primary · 0.2Cool: precise edits, not creative writing
judge · review · secondary · 0.0Ice cold: same input, same verdict, every time

💡
Branch while thinking, not while doing

Exploring three plans as text is cheap. Executing three plans in parallel would triple the cost. So branching happens only in planning, and coding is one plan at a time. Lessons from dead branches feed the next choice, which the docs call the Graph-of-Thought step.

The building inspector who never met the builder

Passing tests isn't the finish line. review sends the jury model the goal, the diff, the step definitions and the green test output, but not the maker's reasoning, so it can't be talked into agreeing. Its prompt opens with: "assume the maker is wrong until proven otherwise."

Routers need hard facts like is_suitable: true, not a paragraph. So every judgment call asks for structured output in JSON. Local models are bad at this, so structured.py works down a ladder of methods:

05

Knowing When to Quit

Failure fingerprints, "same mistake twice" detection, and the budgets that stop an agent from spending forever.

The most expensive bug in AI agents: never stopping

Hikers lost in a forest sometimes carve a mark on a tree. If they pass a tree with their own mark, they know they're walking in circles and should change direction. AI agents get lost the same way. They try the same broken fix again and again, each time saying "this should work now", while the token bill climbs.

The Coding Engineer marks its trees. Every failure gets a fingerprint, and seeing the same fingerprint twice in a row means it's going in circles.

max_attempts_per_plan = 3Tries per plan before giving up on it
max_plans = 3How many strategies to brainstorm
max_total_attempts = 9Hard ceiling across all plans combined
cmd_timeout_s = 120Any single test/lint command is killed after 2 minutes
wall_clock_s = 1800The whole run must finish within 30 minutes
token_budget = 0Optional cap on AI usage (0 = unlimited). A hard stop, not a warning

Taking a fingerprint of a failure

Raw error messages change every time even when the bug hasn't: line numbers move as the code is edited, timestamps tick, memory addresses shuffle. So signatures.py first strips out the parts that churn, then hashes what's left.

Attempt 1: TimeoutError at 2026-07-28 17:43:16 in C:\work\db.py:42 after 3.2s

Attempt 2: TimeoutError at 2026-07-28 17:51:03 in C:\work\db.py:47 after 3.4s

They look different, but it's obviously the same bug.

Attempt 1: TimeoutError at <ts> in <path>:<n> after <dur>

Attempt 2: TimeoutError at <ts> in <path>:<n> after <dur>

Timestamps, paths, line numbers and durations are replaced with placeholders. Now they match. Assertion values are deliberately kept, though: "expected 3 got 5" and "expected 4 got 6" are different failures.

sha1(bdd_gate | test_connect | TimeoutError | <template> | connect)

→ the same short hash both times (an illustrative example here). Same mark on the tree.

Click the tabs to see the normalisation pipeline.

CODE · signatures.py (compute_signature) 
    raw = "|".join(
        [phase, test_name or "", error_class or "", message_template or "", top_frame_func or ""]
    )
    return hashlib.sha1(raw.encode("utf-8")).hexdigest()  # id, not security
PLAIN ENGLISH

Glue five facts together with "|" between them:

which gate failed · which test · what kind of error · the cleaned-up message · the innermost function where it blew up (name only, no line number).

 

Hash it into a short fingerprint. The comment notes SHA-1 is used as an ID here, not for security.

💡
Normalisation is a balancing act

Strip too much and two different bugs look identical, so the agent quits too early. Strip too little and the same bug looks new every time, so it never quits. That's why the docs call the recipe "spec, not implementation detail". When an agent stops too soon or runs forever, the fingerprint recipe is the first place to look.

The doctor's decision tree

Every failure goes to diagnose. An AI classifies the failure (syntax, test-logic, env, flake, design) and writes a lesson, but the routing decision is plain code, checked in this order:

1
Did the user press Stop?

A STOP file on disk means escalate now. It's checked at every diagnose and review.

2
Looks flaky (random)?

Free retry that doesn't count as an attempt, at most 2 times, and never for a repeat fingerprint.

3
Same fingerprint as last time?

The plan is exhausted. Switch to the next-best plan, or escalate if two plans have already died.

4
Any budget blown?

Time, total attempts, tokens, or per-plan attempts mean escalate.

5
Otherwise: a new failure means progress

Retry the same plan with the new lesson.

CODE · nodes.py (diagnose_node) 
    no_progress = prev_signature is not None and signature == prev_signature
PLAIN ENGLISH

"We're stuck" means there was a previous failure and this one has exactly the same fingerprint. Note the flip side: a different failure counts as progress, even if it's still a failure.

🤔
Why stop at two dead plans, not three?

All plans are scored using the same accumulated lessons. If two in a row hit the same wall, the lessons have probably steered into a dead end, and a third plan built on them would likely hit it too. At that point it's cheaper to hand the problem to a person.

The real culprit was the environment

The test process couldn't find the new folder: the worktree root wasn't on Python's import path (PYTHONPATH). No plan could have fixed it, which is why fast escalation was the right call. The flight simulator: practice crashes cost nothing

Pilots learn emergencies in a simulator, where a crash just means pressing reset. Every run of the Coding Engineer gets its own simulator: a git worktree on a fresh branch named coding-engineer/<run_id>. Your own checkout is never touched, and merging is always a human decision.

An approved-tools list for commands

The agent can run programs, but only a handful, and only in a narrow way. Git is especially dangerous, since its options can run arbitrary programs, so even its subcommands are on an allowlist.

CODE · tools/code_exec.py 
_ALLOWED_BINARIES = {"pytest", "ruff", "python", "git"}

_GIT_SUBCOMMAND_ALLOWLIST = {"status", "diff", "add", "commit", "log", "rev-parse"}
PLAIN ENGLISH

Only these four programs may ever be started. Anything else, like curl or rm, is refused outright.

 

Git may only look and save: no push, no reset, no checkout. Flags like -c and --exec are banned too. pip install is blocked unless you explicitly allow it.

Only blame the agent for its own mess

Real repos have old problems. In one live run, app.py already contained a duplicate import os. The maker had to touch that file to fix an import, and the linter blamed it for the old problem. The run escalated 4 times over a line the agent never wrote. The fix: compare against the starting point and count only problems that are new.

💡
Differential checks scale to messy codebases

Tell an AI tool "only fail on lint findings introduced since the baseline commit". This lets strict quality gates work on legacy code without someone first cleaning up years of old debt. The same file also handles moved files: it looks up the old path so moved content isn't treated as brand new.

Your debugging toolkit

When a run behaves strangely, these are the places to look, roughly in order:

📋
run-report.md

Outcome, escalation reason, every plan and score, every lesson with its fingerprint, the final diff. Read this first.

🖨️
Console trace: CODING_AGENT_LOG_LLM=2

One line per AI or tool call, with model, tokens, duration and finish_reason. If that says length, the answer was cut off.

✂️
The 8,192-token cap

One request once produced 84,372 tokens over 675 seconds for a hello-world goal. Now every call is capped (CODING_AGENT_MAX_TOKENS), so a runaway fails fast instead of eating the clock.

🧪
python -m evals.diagnose_llm

Escalating with StructuredOutputError? This shows which JSON methods your model and gateway support. Pin them with CODING_AGENT_STRUCTURED_METHODS.

⏯️
Resume with --run-id · stop with the STOP file

Every step is checkpointed to SQLite. Re-run with the same ID to continue. The UI's Stop button drops a flag the loop checks at the next attempt boundary.

The lesson for steering AI

When a tool-calling agent keeps "calling a tool wrong", don't assume the model is dumb. Ask your AI assistant to "print the generated tool schema". The bug is often in what the model was shown, not in what it did.
