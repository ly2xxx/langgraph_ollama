A Robot That Codes Until It's Done

What the Coding Engineer is, why it exists, and what happens after you hand it a goal.

You give it one sentence. It works until the job is checkably finished.

The Coding Engineer is an AI agent that takes a folder of code plus a plain-English goal, like "implement the string-calculator kata so all scenarios pass". It then writes code, tests it, fixes what broke and tests again, with nobody watching.

A chatbot gives you code and hopes. This agent doesn't hope. It refuses to call a job done until automated tests pass and a second AI has tried to find a cheat.

🎯

Goal-driven

It stops when a test says "done", not when the AI feels done.

🔁

Self-correcting

Each failed test becomes a written "lesson" that feeds the next attempt.

🧱

Sandboxed

It never touches your real files. You review its work and decide whether to keep it.

🛑

Knows when to quit

If it's going in circles, it stops and writes you a report instead of burning money.

The core idea: verification beats intelligence

A mediocre model inside a loop with honest tests will usually beat a brilliant model that just guesses once. The model doesn't do the clever part of this project. The loop around it does. Most of what you'll learn here is about that loop.

The very first lines that run

Everything starts in engine.py, in a function called stream_run. It packs your goal into a starting "clipboard" and hands it to the machine.

CODE · engine.py 
    initial_state: CodingLoopState = {
        "run_id": run_id,
        "target_dir": resolved_target,
        "goal": goal,
        "hitl_bdd_approval": hitl,
        "test_style": "pytest" if str(test_style).lower() == "pytest" else "bdd",
        "budgets": budgets or {},
        # Resolved once up front (not re-derived per node) so the report and
        # any UI show exactly what this run actually used, even if env vars
        # change between this run and the next one.
        "model_info": describe_all(),
    }
    config = {"configurable": {"thread_id": run_id}, "recursion_limit": 150}
    yield from graph.stream(initial_state, config=config, stream_mode="updates")
PLAIN ENGLISH

Build the starting state, a labelled bundle of facts about this run.

A unique ID for this run, used later to resume it after a crash.

Which folder of code to work on.

Your goal, word for word.

Should it pause and ask a human about unclear tests? (Off by default.)

Which testing style: "bdd" (plain-English scenarios) unless you asked for plain "pytest".

Your limits on attempts, time and tokens. Empty means "use the defaults".

Record which AI models are in use now, so the final report is honest even if settings change later.

Bookkeeping: tie saved progress to this run ID, and give up after 150 steps no matter what.

Start the machine and pass along each step's update as it happens, so a UI can show live progress.

🗣️
Vocabulary for steering AI

yield makes this a generator. If you ever want a "live progress" feature, you'd ask the AI to "stream updates from the graph with a generator" rather than "make it show stuff while it runs".
