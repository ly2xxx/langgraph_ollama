Two Brains: Makers and Checkers

Why one AI model proposes and builds, while a different, colder one judges and audits.

Never let the contestant judge the contest

An architecture competition doesn't let the entrants score their own designs. An independent jury does. This agent follows the same rule. Every AI call asks for one of two roles, and the roles can be filled by different LLMs.

🛠️
primary: the contestant

Intake, writing scenarios, proposing plans, coding, diagnosing. These are the frequent, creative calls inside the loop.

⚖️
secondary: the jury

Scoring plans, checking adopted scenarios, adversarial review. These are the independent judgments. If not configured, it falls back to the primary model, so the loop still works with one.

CODE · nodes.py (_score_plans) 
    secondary = _eng().get_llm("secondary", temperature=0.0)
PLAIN ENGLISH

"Give me whichever model plays the jury role, at zero temperature." No node ever builds a model by hand. They all go through get_llm(role), so swapping models is a settings change, not a code rewrite.

propose plans · primary · 0.8Hot: we want three genuinely different ideas
write scenarios · primary · 0.3Slightly warm: some variety, mostly careful
code (maker) · primary · 0.2Cool: precise edits, not creative writing
judge · review · secondary · 0.0Ice cold: same input, same verdict, every time

Tree-of-Thought: brainstorm, then let the jury pick

Before coding, plan_tot runs Tree-of-Thought planning. The primary model proposes k = 3 distinct strategies, and the jury scores each from 0 to 10. When a plan dies, the survivors are re-scored with the lessons learned instead of being thrown away and regenerated. Watch:

P
Planner (primary, 0.8)

Goal: fix flaky DB timeouts. Three ideas: P1 raise the connection pool size. P2 add retry with backoff. P3 switch to an async driver.

J
Judge (secondary, 0.0)

I didn't write these. Scores: P1 8.5 (simplest), P2 7.0, P3 4.0 (big, risky rewrite). P1 is active.

M
Maker

Pool size raised. Tests still time out. Twice, the exact same way. 😩

D
Diagnose

Same fingerprint twice, so P1 is exhausted. Lesson recorded: "Pool size isn't the bottleneck. Timeouts come from network drops."

J
Judge

Re-scoring the survivors with that lesson: P2 jumps to 9.2 because retries directly handle network drops. P3 stays low. P2 is active.

CODE · nodes.py (plan_tot_node) 
    best = max(candidates, key=lambda p: p.get("score", 0.0))
    for p in existing:
        p["status"] = "active" if p["id"] == best["id"] else ("exhausted" if p["id"] in exhausted else "untried")
PLAIN ENGLISH

Among plans that aren't dead yet, pick the one with the highest jury score.

Then go through every plan…

…and label it: the winner is "active", the dead ones stay "exhausted", everything else waits as "untried". The labels show up in the run report.

💡
Branch while thinking, not while doing

Exploring three plans as text is cheap. Executing three plans in parallel would triple the cost. So branching happens only in planning, and coding is one plan at a time. Lessons from dead branches feed the next choice, which the docs call the Graph-of-Thought step.

The building inspector who never met the builder

Passing tests isn't the finish line. review sends the jury model the goal, the diff, the step definitions and the green test output, but not the maker's reasoning, so it can't be talked into agreeing. Its prompt opens with: "assume the maker is wrong until proven otherwise."

CODE · nodes.py (review_node) 
    blocking = [f for f in verdict.findings if f.severity in ("blocker", "major")]
    is_reject = verdict.verdict == "reject" and bool(blocking)
PLAIN ENGLISH

From everything the inspector flagged, keep only the serious problems (blocker or major).

Only count it as a rejection if the inspector said "reject" and backed it with at least one serious problem. A grumpy "reject" over nitpicks gets downgraded to "approve with notes", and the notes go in the report.

Making chatty AIs fill in forms

Routers need hard facts like is_suitable: true, not a paragraph. So every judgment call asks for structured output in JSON. Local models are bad at this, so structured.py works down a ladder of methods:

CODE · structured.py 
_METHODS = ("json_schema", "function_calling")

# Going through an OpenAI-compatible gateway (LiteLLM) to an Ollama backend, the
# json_schema guarantee is gone: langchain-ollama's native `format` parameter is
# no longer in play, so response_format is only advisory and the model can emit
# prose the parser rejects. The gateway still logs 200 OK, which makes this
# failure mode invisible in gateway logs. So put the portable method first for
# OpenAI-family clients and keep json_mode as a third rung.
_METHODS_OPENAI = ("function_calling", "json_mode", "json_schema")
PLAIN ENGLISH

For native Ollama: first try "json_schema", which physically constrains the model so it can only produce valid JSON. If that's unsupported, fall back to tool-calling style.

 

But if you reach Ollama through a gateway…

…that "physical constraint" no longer applies…

…so the model can slip back into prose…

…and the gateway still reports "200 OK" (success), which hides the problem.

So for OpenAI-style clients, lead with the method that works most broadly…

…and keep a third option as backup.

The resulting order for OpenAI-style services.

1

Try each method; on a parse error, retry with the error pasted back in

→
2

Last resort: ask for raw JSON and dig it out of the text

→
3

Still broken? Raise StructuredOutputError and the node escalates instead of crashing
