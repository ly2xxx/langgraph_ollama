Sealing the Exam Before Studying

How the agent writes its own definition of done, then locks it so it can never quietly lower the bar.

The temptation every AI coder faces

Picture a student who writes their own exam and can edit it while taking it. You can guess how they'd do. An AI told "make the tests pass" faces the same temptation: the cheapest fix is often to weaken the test.

The Coding Engineer's answer works like a sealed envelope. The exam is written first and sealed. The student can read it any time but can never change a word.

Step 1: Intake refuses jobs it can't grade

Before anything else, an AI reads your goal and fills in a strict form (the TargetSpec schema). The key box is is_suitable. If the goal can't be turned into things a test could check, the run stops right here.

🌫️

Too vague

"Make the app nicer." What would a test even assert?

🏛️

Architecture calls

"Should we use microservices?" That's a human judgment call.

🔐

Auth & payments

Too risky to hand to an unattended loop.

🚀

Deployments

Touches the real world and can't be undone.

Step 2: The exam is written in plain English

The scenarios use Gherkin, the language of BDD. A matching step-definition file turns each English line into a real check. This is the actual file from the self-rewrite run in Module 1:

CODE · features/migrate_run_maker.feature 
  Scenario: create_agent is actually called inside _run_maker
    Given the source file coding_agent/llm_boundaries.py
    Then "create_agent" should be called within the "_run_maker" function
PLAIN ENGLISH

A named example of what "done" means.

Starting point: look at this specific file.

The check: the new function must really be used in the right place. Importing it isn't enough. This exact scenario failed plan 1 twice and forced the agent onto a different plan.

🧭
Two testing styles

Writing a whole feature file plus step code in one AI call is the most fragile request in the loop. Weaker models can pick test_style="pytest", which skips BDD. The acceptance criteria become the contract, and the maker must write ordinary pytest tests alongside its code.

Step 3: The jail that enforces the seal

The maker AI never touches files directly. Every write, delete or move goes through a Jail object, which checks two things: is this path inside the sandbox? and is it frozen? Watch what happens when the maker gets tempted.

CODE · tools/code_exec.py 
    def _check_frozen(self, real_path: Path, op: str) -> None:
        try:
            rel = real_path.relative_to(self.root)
        except ValueError:
            rel = real_path

        # .git internals are always frozen, even if never explicitly listed.
        if rel.parts and rel.parts[0] == ".git":
            raise JailViolation(f"{op} refused: {rel} is inside .git, which is always frozen")

        for frozen_rel in self.frozen:
            if rel == frozen_rel or self._is_relative_to(real_path, self.root / frozen_rel):
                raise JailViolation(f"{op} refused: {rel} is frozen and cannot be modified")
PLAIN ENGLISH

Before any write/delete/move, check whether the target is off-limits.

Try to express the path relative to the sandbox root…

…e.g. turn "C:/…/worktree/features/x.feature" into "features/x.feature".

If that's impossible…

…just use the path as-is.

 

Git's own bookkeeping folder is always off-limits:

if the path starts with ".git"…

…refuse, with an error message saying exactly why.

 

For every frozen file or folder on the list…

…if this path IS it, or sits inside it…

…refuse. The maker sees this text as a tool error and learns from it.

💡
Loud refusals beat silent ones

The jail raises an exception instead of quietly ignoring bad writes. The tool turns that into an ERROR: … message the AI can read. A blocked action that fails silently teaches the AI nothing and hides bugs from you. A clear refusal is useful feedback.

A real bug: the exam that was already passed

If a feature file already exists in the repo, author_bdd can adopt it instead of writing a new one. That caused one of the project's most instructive failures:

1
An old run left a feature file in the repo

rag_agent_move.feature, from a week-old, unrelated goal.

2
Run 20260808T231438 adopted it as its contract

Its real goal was an AgentExecutor migration. It froze the wrong exam.

3
Every gate went green before any code was written

No failing test ever pushed the maker to change anything.

4
The run escalated with an empty diff

It had dropped two good plans over a problem neither of them caused.

The fix is an adoption gate. A cold, separate AI is asked whether these scenarios actually test this goal. The prompt says it bluntly:
