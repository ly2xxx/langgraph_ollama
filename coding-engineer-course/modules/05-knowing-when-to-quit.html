Knowing When to Quit

Failure fingerprints, "same mistake twice" detection, and the budgets that stop an agent from spending forever.

The most expensive bug in AI agents: never stopping

Hikers lost in a forest sometimes carve a mark on a tree. If they pass a tree with their own mark, they know they're walking in circles and should change direction. AI agents get lost the same way. They try the same broken fix again and again, each time saying "this should work now", while the token bill climbs.

The Coding Engineer marks its trees. Every failure gets a fingerprint, and seeing the same fingerprint twice in a row means it's going in circles.

Taking a fingerprint of a failure

Raw error messages change every time even when the bug hasn't: line numbers move as the code is edited, timestamps tick, memory addresses shuffle. So signatures.py first strips out the parts that churn, then hashes what's left.

Attempt 1: TimeoutError at 2026-07-28 17:43:16 in C:\work\db.py:42 after 3.2s

Attempt 2: TimeoutError at 2026-07-28 17:51:03 in C:\work\db.py:47 after 3.4s

They look different, but it's obviously the same bug.

Attempt 1: TimeoutError at <ts> in <path>:<n> after <dur>

Attempt 2: TimeoutError at <ts> in <path>:<n> after <dur>

Timestamps, paths, line numbers and durations are replaced with placeholders. Now they match. Assertion values are deliberately kept, though: "expected 3 got 5" and "expected 4 got 6" are different failures.

sha1(bdd_gate | test_connect | TimeoutError | <template> | connect)

→ the same short hash both times (an illustrative example here). Same mark on the tree.

CODE · signatures.py (compute_signature) 
    raw = "|".join(
        [phase, test_name or "", error_class or "", message_template or "", top_frame_func or ""]
    )
    return hashlib.sha1(raw.encode("utf-8")).hexdigest()  # id, not security
PLAIN ENGLISH

Glue five facts together with "|" between them:

which gate failed · which test · what kind of error · the cleaned-up message · the innermost function where it blew up (name only, no line number).

 

Hash it into a short fingerprint. The comment notes SHA-1 is used as an ID here, not for security.

💡
Normalisation is a balancing act

Strip too much and two different bugs look identical, so the agent quits too early. Strip too little and the same bug looks new every time, so it never quits. That's why the docs call the recipe "spec, not implementation detail". When an agent stops too soon or runs forever, the fingerprint recipe is the first place to look.

The doctor's decision tree

Every failure goes to diagnose. An AI classifies the failure (syntax, test-logic, env, flake, design) and writes a lesson, but the routing decision is plain code, checked in this order:

1
Did the user press Stop?

A STOP file on disk means escalate now. It's checked at every diagnose and review.

2
Looks flaky (random)?

Free retry that doesn't count as an attempt, at most 2 times, and never for a repeat fingerprint.

3
Same fingerprint as last time?

The plan is exhausted. Switch to the next-best plan, or escalate if two plans have already died.

4
Any budget blown?

Time, total attempts, tokens, or per-plan attempts mean escalate.

5
Otherwise: a new failure means progress

Retry the same plan with the new lesson.

    no_progress = prev_signature is not None and signature == prev_signature
PLAIN ENGLISH

"We're stuck" means there was a previous failure and this one has exactly the same fingerprint. Note the flip side: a different failure counts as progress, even if it's still a failure.

🤔
Why stop at two dead plans, not three?

All plans are scored using the same accumulated lessons. If two in a row hit the same wall, the lessons have probably steered into a dead end, and a third plan built on them would likely hit it too. At that point it's cheaper to hand the problem to a person.

Case study: the confident maker vs. the honest gate

A real run from the README. Goal: "Move rag_research_chatbot.py into a new rag_agent/ subfolder and update its imports."

1
plan-3 chosen (score 9.0). Maker moves the file.

self_check: passed. bdd_gate: ModuleNotFoundError: No module named 'rag_agent'

2
Fingerprint aa7cc6bd. Lesson recorded. Retry.

The maker announces: "All 6 tests pass. The migration is already complete."

3
bdd_gate fails again: aa7cc6bd == aa7cc6bd

No progress. plan-3 is exhausted. Switch to plan-1 (re-scored 7.5).

4
plan-1 hits the same fingerprint

Two plans exhausted, so escalate with two_plans_exhausted. A report is written and the worktree is kept.

🔎
The real culprit was the environment

The test process couldn't find the new folder: the worktree root wasn't on Python's import path (PYTHONPATH). No plan could have fixed it, which is why fast escalation was the right call. Today, the safe command runner adds the worktree to PYTHONPATH for every command. Note also that the maker's "all tests pass" claim was false. Never trust an agent's self-report over a gate.
